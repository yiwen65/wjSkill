# iOS 交易详情页设计评审

## 总体结论

当前方案存在一个 **P0 级风险**：底部按钮文案为“确认”，实际却会立即删除交易，且没有二次确认。用户很难从文案预判结果，误触后又没有拦截，可能造成数据丢失。建议在进入开发前先重做删除流程，再处理信息层级、表单可用性和无障碍问题。

> 已知尺寸仅为设计描述中的正文 `12pt` 与垃圾桶图标 `20×20pt`；以下不对具体设备尺寸作额外假设。

## 问题清单

| 优先级 | 问题 | 影响 | 改进建议 |
|---|---|---|---|
| P0 | “确认”按钮实际执行删除 | 文案与结果完全不一致，用户可能把它理解为保存备注或分类；一旦点击即删除，风险不可接受 | 将编辑操作的主按钮改为“保存”或“完成”，只负责保存；删除应是独立且明确的“删除交易”操作 |
| P0 | 删除前不做二次确认 | 破坏性且可能不可逆的操作没有防误触机制 | 点击“删除交易”后弹出确认界面，明确说明将删除哪笔交易，并提供“取消”和红色破坏性按钮“删除”；若业务允许，再提供短时“撤销”能力 |
| P1 | 垃圾桶图标位于高频触达区域且缺乏文字语义 | 用户可能误触，也可能只看到图标而不理解影响 | 将删除入口与常规编辑动作拉开；可放在更多操作菜单或页面较下方的独立危险区，并使用明确的“删除交易”文案 |
| P1 | `20×20pt` 图标若同时就是点击区域，触控范围过小 | 难以准确点击，对手部控制能力受限的用户更不友好 | 图标视觉尺寸可保留，但应放入至少 `44×44pt` 的可点击区域，并留出与相邻控件的间距 |
| P1 | 商户名与金额都使用 `12pt` 浅灰字 | 金额和商户缺少层级；浅灰文字叠在渐变上可能对比度不足，金额也不易快速扫读 | 把金额设为页面第一视觉层级，商户名作为次级信息；优先使用 iOS 文本样式并支持动态字体，依据渐变的最差背景位置校验文字对比度 |
| P1 | 全宽品牌渐变承载关键内容 | 渐变不同区域的明暗变化会导致可读性不稳定，品牌视觉压过交易信息 | 将渐变视为装饰层；通过稳定的遮罩、纯色内容层或受控配色保证文字在整张卡片上都清晰，并在浅色/深色模式分别验证 |
| P1 | 输入框用 placeholder 代替“备注、分类”标签 | 输入后标签消失，用户无法确认字段含义；读屏和认知可用性也会变差 | 使用始终可见的字段标签，placeholder 只给示例或提示；已有值、空值、错误和禁用状态都应保持字段名称可见 |
| P1 | “分类”被表现为普通输入框 | 分类通常来自有限选项，自由输入可能产生无效值或不一致命名 | 使用可点击的分类选择行或选择器，展示当前分类、进入提示和选中状态；是否允许新建分类应由业务规则决定 |
| P2 | 编辑与删除的操作层级混乱 | 页面既像编辑表单，又把删除包装成主操作，用户无法建立稳定心智模型 | 明确页面模式：详情态提供“编辑”；编辑态提供“取消/保存”；删除始终作为次要的破坏性操作 |
| P2 | 删除确认缺少交易上下文 | 多笔相似交易时，用户无法在最后一步核对对象 | 在确认文案中带上足够辨识该交易的信息，例如商户名与金额；不应只写“确定删除吗？” |
| P2 | 未体现无障碍语义与状态 | 图标按钮、字段及危险操作可能无法被 VoiceOver 正确理解 | 为垃圾桶按钮提供“删除交易”的无障碍标签及必要提示；保证焦点顺序符合视觉顺序，字段状态可被读出，不仅用颜色表达危险或错误 |
| P2 | 未说明键盘、动态字体及底部安全区域下的布局行为 | 输入备注时，键盘或更大字号可能遮挡字段和底部操作 | 让内容可滚动，底部操作避开安全区域和键盘；在动态字体、横竖屏及浅色/深色模式下验证，不预设单一设备尺寸 |
| P3 | 交易详情信息可能不足 | 仅有商户、金额、备注、分类时，用户可能无法核对交易 | 与产品范围确认是否还需日期、账户或支付方式、交易状态等信息；仅在确有用户核对需求时补充，避免无依据堆叠字段 |

## 建议的页面结构

1. **导航区**：显示“交易详情”或“编辑交易”；保留正常返回能力。删除入口放在低干扰位置，不与保存操作并列成同等视觉权重。
2. **摘要区**：品牌渐变可保留，但金额为主信息，商户名为次信息；文字在渐变各区域都应保持清晰。
3. **详情/编辑区**：为“备注”和“分类”设置持久标签。分类使用选择控件，备注使用适合文本输入的控件。
4. **主操作区**：若页面可编辑，主按钮命名为“保存”或“完成”，并只保存更改；无更改时可禁用或隐藏，避免“确认”这种不指明结果的文案。
5. **危险操作区**：独立显示“删除交易”，使用破坏性样式，但避免抢占页面主视觉。点击后进入确认步骤。

## 推荐删除流程

1. 用户点击明确标注的“删除交易”。
2. 系统显示确认界面，并呈现可辨识的交易上下文。
3. 提供两个清晰动作：默认安全动作“取消”和破坏性动作“删除”。
4. 只有点击“删除”后才执行删除；执行期间防止重复提交。
5. 删除成功后返回合理的上一级页面并更新列表；若后端或产品能力允许，提供短时“撤销”。失败时保留当前页面并给出可恢复、可理解的错误反馈。

### 确认文案示例

- 标题：**删除这笔交易？**
- 说明：**“商户名” · “金额”。删除后将无法恢复。**（若支持撤销，应改成与实际恢复能力一致的说明）
- 按钮：**取消** / **删除**

## 验收建议

- 点击“保存/完成”只保存编辑内容，不会触发删除。
- 删除入口名称明确，且不会与普通主操作混淆。
- 删除前必须出现含交易上下文的确认步骤；取消后数据不变。
- 连续点击删除不会重复提交；成功、失败与撤销路径都有明确反馈。
- 商户名、金额及字段标签在渐变、浅色/深色模式和更大动态字体下仍可辨识且不被截断。
- 图标的视觉尺寸与点击区域分离；垃圾桶按钮拥有清晰的无障碍名称。
- 输入内容后，“备注”和“分类”的字段名称仍然可见；分类只能产生业务允许的值。
- 键盘出现、内容滚动和底部安全区域不会遮挡当前字段或关键操作。

## 改版优先顺序

1. 修正“确认即删除”的语义错误，并增加删除确认与失败恢复路径。
2. 拆分保存和删除，重建页面操作层级。
3. 改善金额/商户的视觉层级、文字对比度和动态字体适配。
4. 用持久标签替代 placeholder 标签，并把分类改为选择控件。
5. 完成触控范围、VoiceOver、键盘、安全区域及显示模式测试。
