# 外卖 App 订单列表页：根因分析与修复方案

## 结论摘要

这两个现象不是单纯的“弱网体验差”和“多加一点底部间距”，而是两个状态/布局契约缺失：

1. **请求状态被错误地当成数据状态**：超时或失败落入“订单数组为空”的分支，因此把“未能确认”展示成“确认没有订单”。
2. **固定操作栏没有参与可滚动区域的运行时布局**：底部“再来一单”覆盖列表；iOS 大字体使订单卡片或操作栏增高后，硬编码的高度/间距不再成立。

两项均暂定为 **P1**：前者错误表达关键结果并缺少恢复路径，后者在系统无障碍文字设置下遮挡关键金额。严重度需在真机复现后确认。

## 审查边界与假设

- 已知证据只有用户投诉，尚无截图、布局层级、请求日志、缓存策略、代码或真机复现记录。
- 假设页面至少支持 iOS；最低 iOS 版本、UIKit/SwiftUI/跨端框架、缓存时效和服务端分页协议均未知。
- 以下“根因”是待验证的诊断假设，不冒充已定位的代码事实。
- 证据等级：**A** = Apple/无障碍平台规范或官方指南；**B** = 成熟工程实践；**C** = 本项目可调整的诊断/实现策略。

## 发现 F1：弱网失败被展示成“暂无订单”

- **位置/节点**：订单列表的数据加载状态、空状态组件及请求失败回调。
- **状态与条件**：首次进入或无可见内存数据；网络不稳定、超时、断网或服务端失败。
- **可观察症状**：长时间转圈后出现“暂无订单”，但用户实际有历史订单。
- **证据**：用户投诉（外部任务运行证据，未复现）；“网络失败不能当成空数据”符合事实驱动状态表达原则（A/B）。
- **用户影响**：系统把“无法确认”说成“确认没有”，用户会误以为订单丢失；同时没有明确的重试/离线路径。
- **严重度**：**P1（暂定）**。
- **最小修复**：将 `data`、`request`、`connection` 三个维度拆开；只有一次权威请求成功且明确返回 0 条时才显示“暂无订单”。失败时显示错误和重试；有缓存时保留订单并标记新鲜度。
- **复测方法**：注入慢请求、超时、断网、HTTP/业务错误、断线重连及“成功返回 0 条”场景，逐一核对界面文案、可见数据、重试行为和 VoiceOver 公告。
- **未知项**：空数组是否在请求前初始化；失败是否被统一映射为成功空响应；缓存是否在刷新前被清空；分页首屏/筛选条件是否参与误判。

### 最可能的代码级根因假设

按优先级检查：

1. 模型只有 `loading / orders.isEmpty`，没有 `notFetched / failed / confirmedEmpty`；失败后 `loading=false`，自然进入空状态。
2. 网络层把超时、解析失败或业务错误转换为 `[]`，丢失原始错误类型。
3. 首次刷新先清空列表/缓存，再发请求；请求失败后没有旧数据可回退。
4. 一个全局布尔 `isLoading` 同时驱动首次加载和后台刷新，刷新时整页被阻塞。
5. 请求没有合理的网络层超时与可取消/重试路径，导致旋转反馈持续过久。
6. 首屏分页失败、筛选无结果或账户切换被误归为“全量历史订单为空”。

### 目标状态模型（C 类实现建议）

```text
data:       notFetched | confirmedEmpty | hasData(orders)
request:    idle | firstLoading | refreshing | failed(error, retryable)
connection: online | offline | unstable
freshness:  lastSuccessfulSyncAt | unknown
```

这些维度应允许组合，例如 `hasData + refreshing`、`hasData + failed + offline`，而不是塞进一个互斥枚举。

| 事实组合 | 页面表现 | 推荐文案/操作 |
|---|---|---|
| `notFetched + firstLoading` | 与列表结构接近的骨架或不定进度反馈；保留返回能力 | “正在加载订单…”；不要伪造百分比 |
| `hasData + refreshing` | 旧订单继续可用，仅局部显示刷新状态 | 不清空、不整页遮挡 |
| `hasData + failed` | 保留缓存，显示非阻塞提示与重试 | “更新失败，当前显示截至 14:30 的订单” |
| `hasData + offline` | 保留缓存并明确离线/新鲜度 | “当前离线，显示已缓存订单” |
| `notFetched + failed` | 专用错误状态，不显示空状态 | “订单加载失败，请检查网络后重试”＋“重试” |
| `confirmedEmpty + idle` | 仅在成功、权威响应为 0 条时展示真实空状态 | “暂无订单”＋合理的去下单入口（若业务需要） |
| 当前筛选结果为 0 | 保留筛选条件，区别于账户无订单 | “没有符合当前条件的订单”＋“清除筛选” |

### 数据与交互修复

- Repository 先读本地持久化缓存，再做后台刷新（stale-while-revalidate）；刷新失败不得删除最后一次成功数据。
- 保留结构化错误（离线、超时、服务端、解析、鉴权），由展示层映射成准确且可恢复的状态。
- “暂无订单”的进入条件写成显式谓词，例如：`authoritativeLoadSucceeded && result.isEmpty && noActiveFilter`，不要只判断 `orders.isEmpty`。
- 超时长度沿用并审查现有网络层策略，不在 UI 随意发明固定秒数；超时后停止无限旋转，提供重试，自动重试须有上限并避免请求风暴。
- 后台刷新失败用页面内横幅/局部提示；首次加载失败才使用整页错误状态。
- 分页后续页失败时保留已加载订单，在列表尾部提供局部重试，不能退回整页空状态。
- 埋点至少区分：首次加载耗时、超时/错误类型、错误态曝光、重试成功率、错误后错误进入空状态的次数（目标为 0）。

## 发现 F2：大字体下固定“再来一单”遮挡最后一笔金额

- **位置/节点**：订单列表滚动容器、最后一个订单卡片的金额区域、底部固定操作栏。
- **状态与条件**：iOS 无障碍大字体档位；最后一个订单滚动到列表末尾；可能同时存在 Home Indicator/Safe Area。
- **可观察症状**：固定按钮覆盖最后一个订单金额，内容无法完整阅读。
- **证据**：用户投诉（外部任务运行证据，未复现）；iOS 布局应响应 Dynamic Type 和运行时 Safe Area，关键内容不能被固定控件遮挡（A）。
- **用户影响**：依赖大字体的用户无法核对订单金额；列表虽然能滚动，但最后信息不可达。
- **严重度**：**P1（暂定）**。
- **最小修复**：让底部操作栏成为安全区布局的一部分，并由系统/布局引擎为滚动内容预留其**实际运行时高度**；移除订单卡片和按钮的固定文本高度，金额在大字体时重排而非被裁切。
- **复测方法**：在最小支持机型、全部支持的 Dynamic Type 档位（尤其最大无障碍档位）、深浅色和横屏下，将最后一项滚至底部；检查金额完整可见、VoiceOver 可达、滚动指示器不被覆盖。
- **未知项**：按钮是 overlay、独立 sibling 还是列表 footer；是否使用硬编码 `contentInset`；订单卡片是否固定高度；金额 Label 的压缩优先级/换行策略；实际安全区和组件框架。

### 最可能的代码级根因假设

1. 底部栏以 absolute/overlay 方式盖在列表上，却没有同步列表的 `contentInset`/安全区。
2. 只预留了默认字体下的固定常量；大字体使按钮容器、说明文案或卡片高度变化后，常量失效。
3. 订单 Cell/Card 使用固定高度，金额标签被裁切或与其他文本争夺垂直空间。
4. 修改了视觉 padding，却未同步滚动指示器、VoiceOver 可见区域或运行时 Safe Area。

### iOS 修复方案

**优先方案：布局层级消除覆盖，而非补魔法数字。**

- **SwiftUI**：优先用 `.safeAreaInset(edge: .bottom) { reorderBar }` 放置底部栏，让 ScrollView/List 自动获得可滚动避让区域；栏背景可延伸到底部，但按钮内容留在安全区内。避免同时再加一份固定 bottom padding 造成双重间距。
- **UIKit**：把操作栏与列表作为同一容器的 sibling，操作栏约束到 `safeAreaLayoutGuide`，列表可视底部约束到操作栏顶部；若产品确实要求悬浮覆盖，则根据操作栏**测量后的实时高度**更新 `contentInset.bottom` 和 `scrollIndicatorInsets.bottom`，并在字体/trait/安全区变化时重算。
- **跨端实现**：React Native/Flutter 也应消费运行时 safe-area inset 与操作栏测量高度，不按设备型号或固定像素判断。

订单卡片与按钮本身：

- 使用系统 Dynamic Type 文本样式，允许垂直增长；不要为金额、标题或按钮文案设置只适配默认字号的固定高度。
- 默认字号可横向排列“状态/时间—金额”；进入无障碍大字体后改为上下堆叠，金额单独一行并保持完整。不要通过缩小字号解决。
- 金额是关键内容：提高布局保留优先级，若空间仍不足则换行/重排，不应省略或被覆盖。
- “再来一单”使用系统按钮语义，实际点击区域以 iOS **pt** 计量；项目默认目标可采用至少 **44 × 44 pt**，但须检查运行时 hit region，而不是只看图标或截图像素。
- VoiceOver 顺序应先完整读取订单信息（含金额），再到“再来一单”；按钮需有明确名称、角色和可用状态。

## 联合实施顺序

1. **先复现并采证**：抓取请求时间线、状态迁移、缓存命中及最终 UI 分支；同时记录 iOS 机型、系统版本、Dynamic Type 档位和视图运行时 frame/inset。
2. **修状态模型**：禁止失败转空；接入缓存保留、准确错误和重试路径。
3. **修布局契约**：底部栏进入 Safe Area 布局，滚动容器预留动态高度；订单卡片支持字体增长和重排。
4. **补自动化测试**：ViewModel/Reducer 状态转换单测，列表 UI/snapshot 边界测试，必要时增加“最后一项完全可见”的坐标断言。
5. **真机任务测试**：慢网、离线、重连和最大字体下完成“打开历史订单—核对最后一单金额—点击再来一单”的完整流程，并运行 VoiceOver。
6. **灰度与监控**：对比加载错误、错误误入空状态、重试成功率、页面停留/退出以及重复刷新指标；保留快速回滚开关。

## 必测矩阵与验收标准

### 网络/数据

- 首次安装且有历史订单：慢网、超时、断网、5xx、解析失败、重连。
- 有缓存：后台刷新成功/失败/离线；始终保留旧订单并显示正确新鲜度。
- 真实 0 条、筛选 0 条、第一页成功但下一页失败、账户切换。
- 连续点击重试、返回后再进入、请求乱序返回；旧请求不得覆盖新状态。

### 布局/无障碍

- 最小支持 iPhone、带/不带 Home Indicator 的设备、横屏（若支持）。
- iOS 默认字号到最大支持的无障碍字号；真实长商家名、长状态、最大金额。
- 浅色/深色、显示缩放（若支持）、VoiceOver 与减弱动态效果。
- 最后一条订单滚到底时，金额和所有必要操作均可见、可聚焦、可点击；滚动指示器不被操作栏遮挡。

### 发布阻断条件

- 任一请求失败仍能进入“暂无订单”。
- 有缓存的刷新失败会清空订单，或缓存被当成实时数据而不标记。
- 最大支持字体下最后一笔金额不能完整阅读或 VoiceOver 无法访问。
- 修复依赖某个机型的固定底部数值，或只通过缩小文字来避免覆盖。

## 平台差异

本问题明确发生在 iOS，修复必须使用 iOS Dynamic Type、运行时 Safe Area 和 **pt** 单位验证。若同一代码库也发布 Android，应共享“失败不等于空、缓存须标新鲜度”的语义，但布局改用 Android WindowInsets/实际窗口和 **dp/sp** 验证；不要把 iOS 的 44 pt 或底部常量直接移植为 Android 数值。

## 临时评分与验证边界

按 8 维、32 项审查表，仅有两项由投诉提供有限任务证据：状态/恢复中的“失败被当成空”和无障碍中的“文字缩放丢失内容”；其余 30 项均未验证。将已报告的两项暂记为 Fail、未验证项按下界 0/上界 1 计算，得到 **0–93/100，覆盖 2/32（6.25%）**。这个宽区间不是产品质量分数，只说明当前证据不足；阻断项为 F1、F2，修复并完成上述运行时与辅助技术测试前不得宣称通过。
