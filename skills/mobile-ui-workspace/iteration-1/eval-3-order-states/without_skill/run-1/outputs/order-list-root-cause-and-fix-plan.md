# 外卖 App 订单列表页问题分析与修复方案

## 结论摘要

这两个现象本质上是两类状态建模错误：

1. **网络失败被错误地当成“业务数据为空”**：页面只用一个订单数组同时表达“尚未返回、请求失败、确实无订单”，弱网超时或失败后将数组置空，于是错误展示“暂无订单”。
2. **固定底部操作区未参与列表布局**：按钮通过悬浮/绝对定位覆盖在列表上方，但列表底部只预留了固定高度或没有预留空间；iOS 动态字体使按钮区、订单卡片或金额行高度增加后，预留值失效，最后一项被遮挡。

在没有代码、网络日志和界面层级信息的前提下，以上是与症状最吻合的高概率根因，应先通过下文的埋点和复现步骤确认，避免只改文案或写死更大的间距。

---

## 问题一：弱网后把历史订单显示成“暂无订单”

### 可能的故障链路

典型错误实现可能类似：

```text
进入页面 → isLoading = true → 请求订单
请求超时/断网/解析失败 → catch 中 orders = []
请求结束 → isLoading = false
渲染条件：orders.length == 0 → “暂无订单”
```

这里混淆了至少四种互斥状态：

- 首次加载中；
- 加载成功且确实为 0 条；
- 加载成功且有订单；
- 加载失败/超时，结果未知。

弱网时“转圈很久”还说明请求可能缺少明确的客户端超时、重试上限和加载阶段反馈；最终出现空态，说明异常分支、非 2xx 响应或解析异常很可能被统一转换为空数组。若页面有缓存，还可能在刷新开始时先清空已有订单，导致一次失败抹掉了可展示的历史结果。

另一个需要排查的风险是**请求竞态**：旧请求在新请求之后结束，并用空结果或失败状态覆盖了新请求的成功结果。分页首屏失败时若同时重置列表，也会产生相同现象。

### 如何确认根因

在测试环境使用 Network Link Conditioner/代理工具模拟高延迟、丢包、超时、断网和 5xx，并记录一次请求从发起到页面渲染的完整状态变化。日志和埋点至少包含：

- 请求 ID、用户 ID 的脱敏标识、触发来源（首屏/下拉刷新/分页）；
- 发起时间、耗时、HTTP 状态、网络错误类型、是否超时、重试次数；
- 服务端返回的订单数量、解析是否成功；
- 渲染状态（loading/content/empty/error/stale-content）；
- 缓存命中、缓存条数和缓存时间；
- 请求是否因页面离开或新请求发起而取消。

重点验证：**只有服务端成功返回且解析成功的空集合，才能进入 empty**。若错误或超时之后进入 empty，即可证明状态映射错误。

### 修复方案

#### 1. 建立显式页面状态

不要用 `orders.isEmpty` 推导所有界面状态。建议最少建模为：

```text
initialLoading
content(orders, isRefreshing, isLoadingMore)
empty                 // 仅成功响应 0 条
error(errorType)       // 首屏无可用数据
staleContent(orders, errorType) // 有缓存/旧数据但刷新失败
```

状态转换规则：

- 首次进入且无缓存：显示骨架屏或加载态；
- 请求成功且 `orders.count > 0`：显示内容；
- **请求成功、响应合法且 `orders.count == 0`**：才显示“暂无订单”；
- 首屏请求失败且无缓存：显示错误态，例如“网络不给力，加载失败”，并提供“重新加载”；
- 有缓存或已展示数据时刷新失败：保留原订单，不清空列表；用非阻断提示告知“刷新失败，当前为上次内容”，允许重试；
- 分页失败：保留已有列表，只在列表底部显示分页重试入口。

#### 2. 改善弱网反馈和请求策略

- 为接口配置明确、可观测的连接/读取超时，避免无限转圈；超时值应结合现有接口 SLO 和真实网络数据确定，而不是任意写死。
- 对超时、连接中断等可恢复错误做有限次数、带指数退避和随机抖动的重试；不要自动重试 4xx 或业务错误。
- 加载超过短暂阈值后展示“网络较慢，仍在加载”，并始终保留取消/返回能力；到达超时后切换为可重试错误态。
- 若产品允许，持久化最近一次成功订单快照；离线或刷新失败时显示快照并标注更新时间。缓存不能反过来把未经确认的空结果当成真实空态。
- 刷新开始时不得清空当前数据；只有新请求成功后再原子替换。
- 给请求附加递增序号或使用可取消任务；只允许当前最新请求更新 UI，页面销毁时取消任务。

#### 3. 参考状态更新逻辑

```text
loadOrders():
  requestId = beginLatestRequest()
  if no visible orders:
    state = initialLoading
  else:
    state = content(existingOrders, isRefreshing = true)

  result = await fetchWithTimeoutAndBoundedRetry()
  guard requestId is latest else return

  if result is success:
    if result.orders is empty:
      state = empty
    else:
      saveCache(result.orders)
      state = content(result.orders)
  else if existing/cache orders are available:
    state = staleContent(existingOrCacheOrders, result.error)
  else:
    state = error(mapToUserFacingError(result.error))
```

### 用户可见文案建议

- 空态：`暂无订单`（仅限成功确认无数据）；
- 弱网加载：`网络有点慢，正在努力加载…`；
- 首屏失败：`订单加载失败，请检查网络后重试` + `重新加载`；
- 有旧数据时刷新失败：`刷新失败，当前显示上次加载的订单`。

文案只是状态修复后的表达，不能代替状态机改造。

## 问题二：iOS 大字体下底部按钮遮挡最后一单金额

### 可能的故障链路

底部“再来一单”大概率是固定/悬浮容器，列表则铺满屏幕。当前实现可能存在以下一种或多种问题：

- 列表没有 `contentInset`/底部占位；
- 底部间距写死为按钮常规字号下的高度；
- 未把 iPhone Home Indicator 的 safe area 计入；
- 动态字体使按钮文本、按钮容器或订单卡片换行增高，但底部间距没有随实际高度更新；
- 金额行缺少抗压缩/换行策略，在大字体下被挤到悬浮区后方；
- 只调整了视觉区域，没有同步 scroll indicator inset，用户误以为已滚到底。

因此，单纯把底部 padding 从某个常量调大，只能覆盖少数字号和机型，不是稳定修复。

### 修复方案

#### 优先方案：让操作区参与布局

将页面拆成安全区内的纵向布局：

```text
页面
├─ 可滚动订单列表（占剩余空间）
└─ 底部操作区（由内容决定高度 + safe-area 底部）
```

列表的可视区域自然截止在操作区上方，二者不重叠。这比绝对定位更可靠，也更容易适配旋转、分屏、键盘、安全区和动态字体。

#### 若必须保持悬浮按钮

- 运行时测量底部操作区的实际高度；
- 设置列表底部 `contentInset = 操作区实际高度 + safeArea.bottom + 设计间距`；
- 同步设置滚动条 inset；
- 操作区尺寸变化（动态字体、横竖屏、文案、本地化、安全区变化）时重新计算；
- 最后一个订单还应有正常的卡片间距，不能刚好贴住按钮；
- 在 iOS 中优先用 Safe Area、Auto Layout 和系统动态字体能力，不以机型判断写死数值。

#### 大字体下的内容约束

- 文本使用支持 Dynamic Type 的语义字体样式，并响应 `UIContentSizeCategory` 变化；
- 按钮高度使用“最小高度 + 内容内边距”，不要固定死高度；必要时允许按钮标题换行；
- 订单标题、状态、金额采用可换行或合理的纵向重排，避免金额被截断；金额应完整可读，不应用省略号隐藏关键价格；
- 检查金额与其他标签的 content hugging/compression resistance，保证价格不被低优先级文本挤掉；
- 保持可点击区域至少符合平台可访问性要求，并确保 VoiceOver 焦点顺序与视觉顺序一致。

## 实施顺序

1. **补充可观测性并复现**：记录网络结果到 UI 状态的转换，确认错误为何进入空态；检查底部按钮与列表的布局层级和 inset 来源。
2. **先修正确性**：引入显式加载/内容/空/错误/旧数据状态；失败时不清空历史订单；修复请求竞态。
3. **修复布局**：优先将底部操作区放入正常布局；否则用实测高度动态更新列表和滚动条 inset。
4. **再优化体验**：增加弱网阶段反馈、有限重试、最近成功快照和刷新失败提示。
5. **灰度与监控**：灰度发布后观察错误态、空态、请求成功率和加载耗时，确认空态不再吸收网络错误。

## 验收标准与测试清单

### 订单状态

- 接口成功返回 0 条时，才显示“暂无订单”。
- 接口超时、断网、DNS 错误、5xx、响应解析失败时，无缓存则显示可重试错误态，不显示空态。
- 已有订单时刷新失败，原订单仍可见，并出现非阻断失败提示。
- 有有效缓存且首屏请求失败时，展示缓存、更新时间和失败提示。
- 下拉刷新与自动刷新并发、连续进出页面、前后台切换时，旧请求不能覆盖新请求。
- 分页失败不清空首屏内容，重试后不重复、不漏单。
- 加载态不会无限持续；到达策略规定的超时后进入明确错误态。

### 布局与无障碍

覆盖 iOS 支持范围内的全部 Dynamic Type 档位，尤其是 Accessibility 大字号，并至少测试：

- 小屏和带 Home Indicator 的机型、横竖屏；
- 中文及更长的本地化按钮文案；
- 1 条、很多条订单，金额为长数字，订单标题/状态多行；
- 滚动到最底部时，最后一单的金额和全部可操作内容位于按钮上方，无遮挡、可点击；
- 滚动条终点与真实内容底部一致；
- 字号在页面打开期间变化后，布局能立即重算；
- VoiceOver 可读出最后一单金额和“再来一单”，焦点不被覆盖或困住。

建议增加 UI 自动化断言：将最后一个金额元素滚动到可见区域后，验证其可见矩形不与底部操作区相交；对网络测试使用可控 stub，分别返回成功空数组、成功有数据、超时和失败，断言对应状态互不混用。

---

## 上线监控

建议按 App 版本、网络类型和接口结果分组监控：

- 订单接口成功率、P50/P95/P99 耗时和超时率；
- `empty` 展示次数中对应“成功且 0 条”的比例（目标应为 100%）；
- 错误态重试点击率与重试成功率；
- 使用缓存旧数据的次数及缓存年龄；
- 大字体用户的页面退出率、按钮点击率，以及相关可访问性/UI 自动化失败。

若出现“请求失败但展示 empty”应作为状态不变量告警；若最后一项与底部操作区发生几何相交，应在 UI 回归测试中直接失败。
