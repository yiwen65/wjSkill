# Plan and Execute Tasks

Create one durable task document that is both the execution contract and the
only authoritative status record. Keep facts, assumptions, decisions, work,
and verification evidence traceable to the request and repository.

## Select the mode and authority

Determine the mode from explicit user language:

- Use `plan` when the user requests a plan only or has not clearly authorized
  implementation. In this mode, inspect read-only evidence, create and validate
  the task document, do not start subagents, and do not modify any other project
  file.
- Use `execute` only when the user explicitly authorizes implementation. Limit
  execution to the recorded scope and existing permissions. Planning permission
  alone is not execution permission.
- Treat an explicit request to resume a named task document as continuation of
  that run. Reuse the existing document; do not create a second authority file.
  For every new run, create exactly one new document.

Stop and request confirmation before external writes, destructive operations,
production changes, credential handling, purchases, or any action outside the
recorded authorization. Record the blocked task before asking.

## Establish facts before decomposition

1. Resolve the workspace root and read applicable repository instructions.
2. Inspect the smallest relevant set of source, tests, configuration, history,
   and user-provided artifacts needed to understand the request.
3. Record each material statement as one of:
   - **Confirmed fact:** supported by the request or a cited repository artifact,
     path, command, or observed result.
   - **Assumption:** plausible but not yet verified; include impact and how to
     verify it.
   - **Open question:** only a missing decision that can materially change the
     result, scope, permissions, risk, or deliverable.
4. Ask the smallest focused question only when the answer is material. If work
   can continue safely, record the assumption or deferred question and proceed.

Never convert absence of evidence into a confirmed fact. Treat repository state
as drift-prone and recheck it before execution or resumption.

## Create the authority document

Resolve this Skill's directory and run:

```bash
python3 <skill-directory>/scripts/task_document.py create \
  --root <absolute-workspace-root> \
  --title "<short human title>" \
  --slug <two-to-six-term-kebab-slug> \
  --mode <plan-or-execute>
```

Use a stable lowercase ASCII slug that describes the requirement, not the
implementation attempt. The helper creates
`docs/tasks/<YYYY-MM-DD>-<slug>-task.md`; on collision it inserts `-2`, `-3`,
and so on before `-task.md` without overwriting. It prints the absolute path.

Fill every placeholder immediately. Write prose in the user's language, but
preserve the `<!-- task-doc-section:... -->` markers, task IDs, status enums,
checkboxes, and exact task field keys because the validator uses them. Keep all
required sections generated by the helper:

- background and goal;
- scope and non-goals;
- confirmed facts and evidence;
- assumptions and open questions;
- acceptance criteria;
- dependencies and parallel batches;
- task list;
- test and validation plan;
- risks and blockers;
- execution log;
- final validation result.

Do not maintain a competing checklist, plan file, or status source. A chat plan
may summarize the document but never supersedes it.

## Decompose into verifiable tasks

Use one stable unique ID such as `T-001` for each task. Never renumber an ID
after execution begins. Define each task with all fields in the generated
skeleton:

- `Status`: `pending`, `in_progress`, `blocked`, or `done`;
- `Owner`: coordinator, subagent identifier, or `unassigned`;
- `Objective`;
- `Inputs and prerequisites`;
- `Scope or files`;
- `Expected output`;
- `Dependencies`;
- `Execution steps`;
- `Acceptance criteria`;
- `Verification method`;
- `Validation evidence`;
- `Blocker`;
- `Unblock condition`.

Choose task boundaries by single responsibility, a concrete output, and an
independently runnable verification. Do not split by arbitrary time estimates.
Add newly discovered necessary work as a new task with dependencies and a done
gate; never hide it only in the execution log.

Build an acyclic dependency graph and explicit execution batches. Classify a
task as parallel-ready only when all dependencies are `done`, its inputs are
available, and its owned files/state do not overlap another task in the batch.
Serialize tasks that modify the same file, generated output, shared mutable
state, schema, lockfile, migration chain, or downstream contract. When file
ownership is uncertain, serialize until evidence makes the boundary clear.

## Execute through bounded delegation

In `execute` mode:

1. Update a task to `in_progress`, assign its owner, append the start event to
   the execution log, and validate the document before implementation.
2. Delegate independent, boundary-clear tasks to subagents in parallel when the
   runtime supports subagents. Give each subagent exactly one or an explicitly
   bounded set of compatible task IDs, owned files, prerequisites, acceptance
   criteria, validation commands, and forbidden scope. State that it is not
   alone in the repository, must preserve others' changes, and must not edit the
   authority document unless it has exclusive ownership.
3. Require each subagent to return this structured report:
   - task IDs and completed work;
   - files changed;
   - tests or checks run with actual results;
   - unresolved issues or scope discoveries;
   - recommended status, never a self-approved final status.
4. When concurrent document edits are unsafe, reserve all authority-document
   writes for the coordinator. Integrate every subagent report immediately and
   serially.
5. Inspect each diff and rerun the smallest meaningful verification. Treat a
   subagent report as evidence to examine, not proof of completion.
6. Integrate compatible results, resolve conflicts, and run dependency-path and
   cross-task checks before releasing downstream batches.

If parallel-ready tasks exist but the runtime cannot start subagents, mark them
`blocked` with that evidence and request authorization before changing to a
sequential execution strategy. Do not simulate delegation or claim parallel
execution. A purely serial graph may be executed by the coordinator.

## Maintain truthful state

Use only these transitions:

- `[ ] pending` -> `[ ] in_progress` when work actually starts;
- `[ ] in_progress` -> `[ ] blocked` when progress requires an unmet condition;
- `[ ] blocked` -> `[ ] in_progress` after the condition is satisfied;
- `[ ] in_progress` -> `[x] done` only after implementation and required
  verification both pass.

For `blocked`, record the reason, evidence already collected, and exact unblock
condition. For `done`, replace `Validation evidence: Not run.` with actual
commands/checks, results, and limitations. Never mark partial, unverified, or
subagent-claimed work `done`. Never use `[x]` with any other status.

Append concise timestamped events to the execution log after every state change,
handoff, integration, validation, blocker, and material decision. On interruption,
leave no task `in_progress` unless its owner and resumable next action are clear.
On resumption, read the entire authority document, refresh repository status and
drift-prone evidence, reconcile claimed states with artifacts, and continue from
the dependency graph.

## Validate the plan and outcome

After initially filling the document, after material status edits, and before
final reporting, run:

```bash
python3 <skill-directory>/scripts/task_document.py validate \
  --path <absolute-task-document>
```

The validator checks required sections, task fields, unique IDs, dependency
references and cycles, checkbox/status consistency, and evidence requirements
for `blocked` and `done`. It cannot prove that evidence is true; the coordinator
must inspect artifacts and rerun available checks.

For every implementation task, select the smallest effective unit, integration,
static, build, format, contract, or smoke check supported by the repository.
Before overall completion:

- verify every task output against its acceptance criteria;
- verify dependency and integration paths;
- check for regressions and untracked necessary work;
- record exact commands, results, and validation limits;
- state why any planned test could not run instead of saying it should pass.

Set the final validation section to `passed` only when all required tasks are
`[x] done`, the document validator passes, and the overall acceptance criteria
have current evidence. Otherwise record `partial`, `failed`, or `blocked` with
the remaining task IDs and conditions.

## Report completion

Return the absolute task-document path, mode, completed and blocked task IDs,
files changed, checks actually run, final validation result, and remaining
limits. In plan mode, explicitly state that no implementation or subagent
execution occurred.
