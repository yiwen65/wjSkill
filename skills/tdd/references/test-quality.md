# Test Quality

Use this reference when selecting a test seam or strengthening a test that does
not reliably specify behavior.

## Choose the smallest stable seam

Test at the closest public boundary that can observe the requested behavior:

| Behavior | Usually start at |
| --- | --- |
| Pure domain rule | Exported function or public object method |
| Service workflow | Public service or use-case interface |
| HTTP behavior | Route through the real router, with external boundaries controlled |
| UI behavior | User-visible interaction and rendered result |
| CLI behavior | Arguments, exit status, stdout/stderr, and intended side effects |
| Previously reported bug | Narrowest public reproducer of the failure |

A broader test is not automatically stronger. Prefer the lowest level that
would fail for the real defect while remaining stable across internal
refactors. Add end-to-end coverage only when the behavior depends on wiring or
integration that a narrower seam cannot prove.

## Use an independent oracle

Expected values must come from a source that can disagree with the production
algorithm: a requirement, a known literal, a worked example, a protocol rule,
or an approved fixture.

```typescript
// Weak: reproduces the implementation's likely calculation.
const expected = items.reduce((sum, item) => sum + item.price, 0);
expect(calculateTotal(items)).toBe(expected);

// Strong: uses a worked example with a known result.
expect(calculateTotal([{ price: 10 }, { price: 5 }])).toBe(15);
```

Avoid assertions that compare a value to itself, snapshots accepted without
review, or expected data generated by the code under test.

## Specify behavior, not structure

Prefer names such as `returns the saved user by id` over `calls repository.find`.
Verify the result through the public interface. A refactor that preserves the
contract should not require the test to change.

One behavior can require several assertions. For example, a CLI error contract
may include its exit status, error message, and absence of an output file. Keep
those assertions together when they describe one outcome.

## Check sensitivity

The observed red state is the primary proof that the test can detect the missing
or incorrect behavior. If the test passes before implementation, determine
whether the behavior already exists, the test reaches the wrong seam, or the
assertion is too weak before continuing.
