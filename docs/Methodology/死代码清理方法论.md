## 1\. 执行摘要

### 1.1 核心结论

**Dead code 清理本质上不是一次静态扫描，而是一次受控的系统行为变更。**

对于大型仓库，删除安全性可以概括为：

任意一项为零，都不应直接删除。

其中：

1. **边界封闭** ：已知所有入口、构建目标、运行环境、消费者、配置变体和兼容版本。
2. **多源证据收敛** ：静态分析、运行时观测、接口与所有权调查等相互独立的证据得出一致结论。
3. **反事实验证** ：不仅“从未看到它被调用”，还要验证“停掉入口后系统仍正常”。
4. **可恢复发布** ：删除可通过版本回滚、镜像回退、Feature Flag 或兼容实现快速恢复，且没有不可逆数据变化。

CodeQL 官方的“查找未调用方法”示例明确指出，简单调用图查询通常会产生大量结果，必须排除隐式调用、公开入口和库代码；SpotBugs 也明确提示，所谓未调用私有方法可能由反射使用。Knip 对动态 import、生成文件、自动导入和不完整框架插件配置同样列出了专门的误报处理路径。 [^1]

### 1.2 最终决策原则

| 问题 | 结论 |
| --- | --- |
| **什么条件下可以删除？** | 清理边界明确；无近期正向调用；静态、运行时和消费者证据相互印证；不存在外部兼容、动态注册、数据或低频恢复风险；全量构建、测试和契约验证通过；可灰度、可监控、可回滚。 |
| **什么情况下不能删除？** | 唯一依据是 IDE 提示、低覆盖率、Git 历史久或生产日志无记录；消费者未知；存在反射、插件、跨仓、公开 API、旧移动端、数据库、消息回放、定时任务或灾备路径；没有足够观察窗口；没有可靠回滚方案。 |
| **删除后如何证明仍然安全？** | 通过删除前的禁用或隔离实验、全构建矩阵、自动化测试和契约测试、灰度与对照指标、未知调用告警、完整观察窗口以及可执行的回滚演练，形成有明确边界和期限的“工程保证”。 |

> **正向使用证据优先级最高。** 一次可信的生产调用、外部消费者确认或必要的故障恢复演练，就足以推翻大量“未发现引用”的负向证据。

## 2\. Dead code 的分类与判断难点

## 2.1 建议采用的工作定义

**\[综合建议\]**

在给定的：

- 支持版本；
- 构建目标；
- 配置组合；
- 入口集合；
- 运行环境；
- 消费者范围；
- 时间窗口；

之内，某项代码或相关工程资产：

1. 不可能影响受支持的系统行为；
2. 不属于仍有效的内部或外部契约；
3. 不承担回滚、迁移、灾备、审计或兼容职责；
4. 删除后能够通过工程验证证明行为保持不变；

才可以称为 **已验证 dead code** 。

仅由工具报告的项目，应称为 **dead-code candidate** ，而不是 dead code。

## 2.2 分类

| 类型 | 定义 | 典型例子 | 关键判断 |
| --- | --- | --- | --- |
| **不可达代码** | 从所有合法入口都不存在可行控制流路径 | `return` 后语句、恒假条件分支、不可能匹配的 case | 若由编译器在单一函数内证明，置信度较高；跨函数、跨配置时仍需验证 |
| **语义无效代码** | 可能执行，但结果不能影响任何可观察行为 | 写后未读、纯函数返回值被丢弃、重复赋值 | 必须确认调用没有副作用；“返回值未用”不等于“调用无用” |
| **未使用的局部或私有声明** | 在可见作用域内没有引用 | 局部变量、私有函数、私有字段 | 在封闭源码边界内通常风险最低，但反射和框架扫描仍可能绕过显式引用 |
| **未使用的导出、包、文件或依赖** | 仓库内没有找到消费者 | 公共函数、导出类、npm 依赖、共享库 target | 可能被跨仓、插件、脚本、外部客户或发布包使用 |
| **废弃但保留的 API** | 已声明不再推荐，但仍处于兼容期 | `/v1` API、废弃 SDK 方法、旧 CLI 参数 | **不是 dead code** ；只有消费者迁移和废弃窗口结束后才成为删除候选 |
| **无流量业务路径** | 在观测期内没有触发 | 低频退款、年度结算、灾备切换、特定地域流程 | 无流量只是观测结果，不是不可达性证明 |
| **无效配置、Flag 与兼容代码** | 配置或 Flag 已失去可变化性，旧兼容分支不再服务受支持版本 | 永久为 true 的 Flag、旧环境变量、协议兼容 shim | 必须同时核对控制面、部署清单、客户端版本和历史数据 |
| **重复实现与迁移残留** | 新旧实现共存，旧实现疑似不再承担职责 | 双写、双读、旧 DAO、旧序列化器 | 重复可能承担回滚、校验或迁移任务，不能仅凭“功能相同”删除 |
| **测试、示例和夹具残留** | 只被测试或文档环境使用，或已经失去对应生产行为 | fixture、示例应用、测试 helper | 示例可能属于公开 API 文档；fixture 可能支撑兼容、升级和回归测试 |
| **仅特定构建目标使用的代码** | 默认构建不使用，但某平台或产品变体仍使用 | Android flavor、编译宏、Go build tag、Rust feature | 必须覆盖完整构建矩阵，不能只看默认 target |

Rust 的 `dead_code` lint 就明确限定为未使用的未导出项；IntelliJ 的项目级“Unused declaration”也依赖配置的入口点、测试范围、模块描述和自定义注解。这说明“unused”结论天然依赖分析边界。 [^2]

## 2.3 为什么“当前未观测到使用”不等于“可以安全删除”

| 原因 | 示例 |
| --- | --- |
| **观测不完整** | Trace 采样只保留部分请求；子进程、异步消费者或批处理未接入埋点 |
| **时间窗口不代表完整业务周期** | 月末结算、季度报表、证书轮换、年度任务、灾备演练 |
| **环境和用户分群未覆盖** | 特定地域、租户、角色、权限、硬件、云环境、移动端版本 |
| **消费者不在当前仓库或观测域** | 外部客户、合作方、运维机器、离线脚本、内部未登记仓库 |
| **动态机制绕过显式引用** | 反射、字符串类名、依赖注入、插件注册、动态 import |
| **代码承担待机或恢复职责** | fallback、数据回滚、兼容旧格式、重放历史消息 |
| **代码通过加载产生副作用** | 静态初始化、包 `init` 、注册表写入、CSS/polyfill import |
| **遥测本身可能有偏差** | 采样、日志限流、指标标签缺失、监控只覆盖成功路径 |

OpenTelemetry 明确把采样定义为控制保留 Span 数量和开销的机制；父级采样与异步生产者—消费者链路还可能造成链路不完整。因此，“采样 Trace 中没有看到调用”只能构成限定条件下的负向证据。 [^3]

同样，代码覆盖率描述的是某次测试运行执行了哪些行或分支；它不证明未覆盖部分在生产中无用，也不保证所有并发、子进程和动态上下文都被正确采集。 [^4]

## 3\. 主流方法对比表

### 证据强度定义

- **线索** ：用于生成候选，不能独立支持删除。
- **支持性证据** ：能降低风险，但仍需其他独立证据。
- **边界内强证据** ：在明确封闭边界内可以满足某个删除门槛，但仍需构建、测试和回滚验证。

| 方法 | 基本原理与可发现对象 | 典型误报 | 典型漏报 | 大仓库成本、前置条件与局限 | 能提供的证据 |
| --- | --- | --- | --- | --- | --- |
| **编译器和 IDE 检查** | 词法作用域、类型解析、局部控制流；发现未使用变量、参数、私有成员和显式不可达语句 | 反射、注解入口、框架回调、测试发现机制 | 导出 API、字符串调用、跨进程消费者 | 成本低；必须使用正确编译参数、源集和入口配置；不同 IDE 配置可能不一致 | 私有、局部、封闭范围内可为强证据；其他情况仅是线索 |
| **静态调用图与可达性分析** | 从入口集合构建 call graph，查找没有入边或不可达节点 | 动态调用边未建模，导致实际使用项被报死 | 保守加入过多可能调用边，导致真正死代码仍被认为可达 | 全局分析计算和存储成本高；需要完整依赖、源码和框架模型；全程序分析通常无法覆盖开放世界 | 支持性证据；完整 closed-world 模型下可较强 |
| **数据流、控制流和语义查询** | 跟踪值、调用目标及控制流，例如 CodeQL 自定义查询 | source/sink、入口或框架模型配置错误 | 分析为控制成本而限制范围；外部库或运行时行为不可见 | 全局数据流开销明显高于局部分析；需专家编写和维护查询 | 复杂场景中的支持性证据 |
| **构建依赖图** | 分析 target、package、artifact、toolchain 和生成动作依赖 | 未声明依赖、运行时加载和手工脚本不在图中 | 某 target 被保留但其中符号全部无用 | 适合 monorepo；必须覆盖 `select` 、平台、feature、toolchain 和生成规则 | 对 target/package 层面的边界内强证据 |
| **代码、字符串和仓库搜索** | 搜索符号名、路由、topic、配置 key、文件名和字符串引用 | 同名字符串、注释和文档噪声 | 拼接名称、哈希、别名、生成代码、未索引仓库 | 低成本但容易被误当成证明；必须搜索代码、配置、IaC、脚本、文档及其他仓库 | 线索或支持性证据 |
| **Git 历史和代码所有权** | 通过 `log` 、 `blame` 、迁移 PR、CODEOWNERS 和 issue 理解来源与责任人 | “多年未改”可能是稳定核心代码 | 最近引入的代码也可能已经无用 | 跨组织找负责人耗时；CODEOWNERS 是审查责任，不等于实际消费者 | 治理和上下文证据，不是可达性证据 |
| **测试覆盖率** | 运行时插桩，记录测试执行的行、分支或上下文 | 缺少测试导致活代码被当成死代码 | 测试为了覆盖而执行已经无业务意义的代码 | 低质量测试环境中价值有限；需要合并单元、集成、端到端和不同进程数据 | “被执行”是强反证；“未执行”只是线索 |
| **运行时计数、日志与调用追踪** | 在函数、Handler、API、Flag 或任务入口记录调用和消费者信息 | 采样、埋点缺失、标签不完整导致假零调用 | 已执行的辅助代码仍可能没有业务必要性 | 存储、性能、隐私和指标基数成本；需覆盖异步、批处理和失败路径 | 正向调用是强反证；代表性窗口内零调用是支持性证据 |
| **API、Schema 与契约验证** | 对 HTTP、RPC、Protobuf、消息和包接口做兼容差异与消费者契约验证 | 未登记消费者、契约集过期 | 契约只覆盖被表达出的交互，不覆盖语义和运维依赖 | 需要服务目录、schema 仓库或 Contract Broker；跨团队协调成本高 | 对已登记消费者是强证据，对未知消费者不是 |
| **配置、DB、MQ、调度和脚本盘点** | 把非代码入口纳入依赖图：配置 key、表字段、topic、cron、runbook | 资产登记过期 | 临时人工执行、历史消息重放、外部 BI/ETL | 往往是最昂贵、但最关键的调查；需要平台、数据和 SRE 参与 | 高风险项的必要支持证据 |
| **Feature Flag 生命周期治理** | 记录 Flag owner、创建时间、预期寿命、评估次数和固定值，清理输掉分支 | 环境未覆盖、客户端本地 Flag、不上报评估 | Flag 固定但两分支仍有状态或数据差异 | 需要统一 Flag 平台和命名；状态变更 Flag 必须跨发布周期清理 | Flag 状态是线索；禁用分支观察是强证据 |
| **Deprecation 与迁移流程** | 阻止新消费者、通知现有消费者、提供替代项和 Sunset 时间 | 消费者未接收或忽略通知 | 隐蔽消费者继续调用 | 时间和协调成本高，但公开接口不可省略 | 是删除前置过程，不直接证明无消费者 |
| **自动化删除或 codemod** | 用 AST、CST 或规则引擎批量移除已确认模式 | 规则漏建副作用、动态引用或语言特性 | 只能处理规则覆盖的模式 | 大规模收益高，但变更爆炸、许可和版本兼容需审查 | 机械执行能力，不是删除证据 |
| **CI、构建、测试、灰度和监控** | 在变更后验证可构建、契约兼容、行为和生产指标稳定 | 测试与指标盲区导致假安全 | 无法证明未来低频路径 | 是必要门禁；大仓库应采用已有问题 baseline，仅阻止净新增 | 删除后的验证证据 |

CodeQL 官方说明，全局数据流比局部数据流消耗更多计算资源，并且外部库源码、运行时决定的调用目标和别名都会增加完整建图难度。 [^5]

Bazel `query` 分析的是声明的 BUILD 依赖图，而 `cquery` 才会处理 `select()` 等配置影响， `aquery` 则暴露动作和产物；三者都主要解决 target 和 artifact 层问题，并不直接证明某个源代码符号无用。 [^6]

## 4\. 高风险误判场景及验证措施

| 高风险场景 | 静态分析为什么容易误判 | 必须补充的验证措施 | 自动删除判定 |
| --- | --- | --- | --- |
| **反射与动态分发** | 调用目标由类名、方法名、类型信息或运行时对象决定 | 搜索反射 API 和字符串来源；采集实际解析目标；检查 native/trimming 配置；保留带原因和期限的入口 allowlist | 未建立动态目标清单前禁止 |
| **依赖注入和框架自动注册** | 构造函数或组件没有显式调用，靠注解、扫描或容器注册 | 导出容器注册表；启动 smoke test；检查扫描包、模块配置和注解；按真实生产 profile 启动 | 注册模型不完整时禁止 |
| **动态 import** | 模块名运行时拼接或来自配置 | 搜索 import API；记录解析后的模块；列出 import map；覆盖插件和部署配置 | 名称域不能穷举时禁止 |
| **代码生成、宏、AOP 和 annotation processor** | 分析对象可能是生成前源码或生成后产物，调用边不存在于同一阶段 | 分析 generator、模板和生成 manifest；运行完整生成动作；对生成前后分别建图；禁止直接修改可再生成产物 | 未纳入生成流水线时禁止 |
| **插件、扩展点与回调** | 插件由 manifest、SPI、包扫描、文件系统或第三方加载 | 建立插件目录和版本清单；收集加载与激活指标；执行插件兼容测试；联系插件所有者 | 属于开放世界，默认不得自动删除 |
| **配置、环境变量和字符串引用** | 没有语言级符号关系，值可能来自部署平台或 Secret | 搜索 Helm、Terraform、Kustomize、CI、启动脚本和配置中心；先对旧 key 增加使用告警；覆盖环境矩阵 | 配置来源不完整时禁止 |
| **RPC、HTTP、CLI** | 消费者位于进程外或仓库外 | API gateway 和服务网格日志；按 consumer ID、token、User-Agent、版本观测；服务目录；契约测试；全组织代码搜索 | 未知外部消费者时进入废弃流程 |
| **消息队列与事件订阅** | 离线消费者、暂停订阅和历史消息重放不会产生近期流量 | broker subscription 清单；consumer group 状态；schema compatibility；回放测试；保留周期调查 | Topic、字段、事件类型不得直接删除 |
| **定时任务和运维脚本** | 不由主程序调用，可能一年仅执行一次或人工触发 | 调度平台、审计日志、runbook、工单和堡垒机脚本盘点；先停止调度，不立即删代码 | 至少覆盖两个预期执行周期 |
| **数据修复与迁移脚本** | 常态无调用，但事故或迁移时关键 | 确认迁移完成和数据留存期；归档可执行包与说明；验证备份和替代恢复路径 | 通常先归档，不做自动删除 |
| **跨仓、外部客户和第三方调用** | 当前仓库内零引用不代表公开接口无人用 | 全组织代码搜索、包注册表、API 日志、客户通知、消费者确认、Deprecation 与 Sunset | 未完成消费者迁移时禁止 |
| **移动端旧版本** | 服务器仓库无法看到仍在用户设备上的旧代码 | 按 App 版本分析流量；确定最低支持版本、强制升级和应用商店分布；覆盖离线后重新上线客户端 | 支持窗口结束前禁止 |
| **地域、租户、权限或低频路径** | 默认测试和主区域流量不覆盖条件组合 | 按地域、租户、角色、权限和产品档位分桶；合成调用；故障演练或 game day | 未覆盖关键分桶时禁止 |
| **故障恢复、降级和灾备路径** | 正常运行时天然无流量 | 故障注入、灾备切换演练、tabletop、恢复 runbook 审查；验证替代机制 | 属于直接阻止自动删除的条件 |
| **测试发现、fixture 和示例** | 测试框架通过命名、注解或反射发现；示例可能不被编译 | 执行测试发现列表；构建 examples/docs；检查发布包和用户文档；确认是否属于支持契约 | 仅在所有相关 target 验证后人工删除 |
| **特定构建目标或平台** | 默认构建没有启用宏、feature、flavor、arch 或 tag | 枚举 CI 和发布系统实际使用的配置；构建每种受支持组合；分析 Bazel `cquery` 等配置图 | 构建矩阵不完整时禁止 |
| **导入或初始化副作用** | 符号未引用，但 import、静态块、 `init` 或构造过程完成注册 | 启动行为对比；扫描初始化器；检查 bundler `sideEffects` ；记录注册前后差异 | 副作用未证明可移除时禁止 |
| **数据库和持久化格式** | 读取代码已消失不代表历史数据、CDC、BI 或回滚不再依赖字段 | 查询读写路径、CDC、ETL、报表、备份和回滚；停止写入→等待留存期→删除读取→最后删 schema | 不允许自动删除 |
| **安全、计费、权限和审计** | 调用低频，但错误后果高；部分逻辑有意隐藏 | 安全/财务/合规负责人审批；威胁建模；对账；审计与演练 | 直接阻止自动删除 |

Webpack 官方文档特别指出，tree shaking 依赖静态 ES Module 结构和正确的 `sideEffects` 声明；错误地标记 `sideEffects:false` 可能移除 CSS、polyfill 或其他副作用代码。这类“最终包里没出现”只能说明某一构建产物进行了消除，不能直接推出源码可删。 [^7]

在.NET 中，官方 trimming 文档同样要求通过 `DynamicDependency` 、 `DynamicallyAccessedMembers` 等方式描述反射依赖，并明确指出许多基于反射的序列化路径无法被静态分析完整理解。 [^8]

## 5\. 端到端安全清理 SOP

## 5.1 先建立统一的候选项记录

每个候选至少包含：

| 字段 | 内容 |
| --- | --- |
| `candidate_id` | 唯一编号 |
| `artifact` | 符号、文件、target、依赖、配置、API、Flag、topic 或 schema |
| `type` | 第 2 节中的分类 |
| `scope` | 仓库、模块、服务、构建目标和环境边界 |
| `entrypoints` | 所有可能入口 |
| `build_matrix` | 平台、profile、feature、region、tenant、版本 |
| `static_evidence` | 工具、版本、配置和原始结果 |
| `runtime_evidence` | 指标、Trace、日志、覆盖数据和观察窗口 |
| `consumer_evidence` | 仓库搜索、服务目录、API、包和所有者确认 |
| `business_criticality` | 普通、客户关键、数据、计费、安全、控制面、灾备 |
| `owner` | 代码负责人和业务负责人 |
| `recovery_plan` | revert、镜像回滚、Flag、兼容包、数据恢复 |
| `decision` | 自动删、人工删、迁移、暂缓 |
| `expiry/review_date` | 暂缓项和 suppression 的复查日期 |

## 5.2 分阶段 SOP

| 阶段 | 输入 | 核心操作 | 输出 | 责任角色 | 风险控制 | 下一阶段门槛 |
| --- | --- | --- | --- | --- | --- | --- |
| **0\. 确定边界和成功标准** | 业务目标、仓库与系统清单 | 明确支持版本、入口、配置矩阵、外部消费者、排除区；定义安全和效果指标 | 治理章程、范围图、停止条件 | 架构负责人、业务负责人、SRE | 高风险域默认排除；禁止用 LOC 作为唯一目标 | 范围和风险偏好经负责人批准 |
| **1\. 建立基线** | 构建、测试、依赖、生产指标 | 记录构建时间、包体积、依赖数、测试时长、SLO、错误率；盘点 API、job、topic、Flag、配置 | 可重复的基线报告 | 平台工程、SRE、QA、模块负责人 | 固定工具版本与构建参数；标记遥测盲区 | 基线可重复生成，覆盖边界已知 |
| **2\. 生成候选清单** | 编译器、IDE、静态图、构建图、覆盖和搜索 | 多工具 report-only 扫描；合并、去重；记录工具配置 | 候选 ledger | 平台团队、语言专家 | 不自动改代码；保留原始证据 | 每个候选可复现，来源可追踪 |
| **3\. 分类和风险分级** | 候选 ledger | 区分局部、导出、公开、动态、数据、运维、恢复路径；应用 veto 条件 | 风险级别和建议路径 | 架构师、模块 owner | 高风险条件直接降级为“迁移/暂缓” | 分类和关键性均已填写 |
| **4\. 识别负责人和消费者** | CODEOWNERS、历史、服务目录、日志、仓库清单 | 查询 Git 历史和迁移背景；搜索全部相关仓库和配置；联系消费者 | owner 与 consumer 清单 | 模块 owner、API owner、项目经理 | “未找到 owner”不能解释为“无人使用” | owner 明确；未知消费者风险已关闭或记录 |
| **5\. 多源独立验证** | 静态、动态、契约和历史数据 | 至少从不同证据族交叉验证；检查所有 build/profile；核对遥测采样和观察周期 | 证据包与评分 | 架构师、平台、SRE、QA | 两个使用同一 AST 的工具不能视作两个独立证据 | 达到对应决策类别门槛 |
| **6\. 先停止入口或废弃** | 已验证候选、回滚设计 | Flag 固定值；停止调度；阻止新消费者；API 标记 deprecated；旧入口增加告警 | 进入不可新增使用状态 | API/模块 owner、SRE | 保留旧实现；所有命中都告警；不得同时做不可逆数据变更 | 观察期内无意外使用和业务回退 |
| **7\. 隔离与反事实验证** | 已停入口的系统 | 从注册表移除、从默认构建排除、路由到新实现或 shadow；观察系统是否仍正常 | “没有旧路径也能运行”的证据 | 模块 owner、SRE、QA | 可一键恢复；明确停止阈值 | 无未知调用、SLO 和数据一致性正常 |
| **8\. 设计小型删除变更** | 通过验证的候选 | 一个 PR 只处理一个逻辑主题；避免格式化、升级和重构混入；先删入口，再删实现 | 可审查、可 revert 的 PR | 开发者、代码 owner | 机器生成 diff 必须人工审查；记录恢复 commit | reviewer 能完整理解影响面 |
| **9\. 构建、测试和契约验证** | 删除 PR | 编译全部 target/profile；单元、集成、端到端、启动 smoke、契约、schema、安装包和升级测试 | CI 证据报告 | QA、平台、服务 owner | 覆盖 n/n−1 滚动部署与旧客户端；失败即停止 | 所有强制门禁通过，无 unexplained skip |
| **10\. 灰度发布** | 可发布构建、回滚资产 | 小比例实例/租户/地域灰度；与 control 比较错误率、延迟、业务和资源指标 | 灰度评估 | SRE、发布负责人 | 自动或人工 halt；旧镜像和配置可用 | 所有预定 guardrail 通过 |
| **11\. 生产观察与回滚** | 灰度及全量发布 | 覆盖完整业务周期；监控旧入口命中、SLO、工单、数据差异和消费积压 | 最终验收或回滚记录 | SRE、业务 owner | 任何未知消费者或数据异常立即回滚 | 观察窗口结束且无相关回归 |
| **12\. 清理关联资产** | 已确认安全的删除 | 删除依赖、配置、Flag、测试、文档、告警、dashboard、runbook、权限和构建规则 | 完整清理 PR、更新架构清单 | 模块 owner、文档/平台/运维 | 数据 schema 和外部 API 仍遵循独立生命周期 | 无悬空引用，资产登记同步完成 |
| **13\. 纳入持续治理** | 候选数据和复盘 | CI 阻止净新增；suppression 要有 owner、理由和过期日；定期复扫和回归抽样 | 持续治理机制 | 架构治理团队、平台团队 | 先 baseline 旧问题，不一次性阻塞整个仓库 | 候选精确率、处理 SLA 和事故率达标 |

JetBrains Qodana 的 baseline 机制会区分已有、净新增和已消失的问题，适合大仓库采用“先记录存量，只阻止新增”的渐进式接入方式。 [^9]

Google SRE 公开实践强调小批量变更和 canary 对照，以限制故障半径并提高问题归因能力；其配置管理实践还指出，在事故中回滚通常比现场修补更快、更安全。 [^10]

## 5.3 不同资产的推荐清理顺序

| 资产 | 推荐顺序 |
| --- | --- |
| **普通内部函数** | 禁止新引用 → 静态与测试验证 → 小 PR 删除 → 灰度 |
| **Feature Flag** | 确认最终值 → 对输掉分支增加命中指标 → 在所有环境固定状态 → 删除输掉分支 → 发布完成后再删 Flag 配置和平台记录 |
| **公开 API** | 冻结新增消费者 → 标记 Deprecated → 提供替代项和迁移文档 → 逐个迁移消费者 → 发布 Sunset 时间 → 观察零调用 → 删除或保留可监控 tombstone |
| **配置项** | 标记废弃 → 读取时发出带消费者信息的告警 → 部署配置停止下发 → 固化默认行为 → 删除解析与 schema → 最后删除 IaC 和文档 |
| **定时任务** | 停止调度 → 保留可手工恢复的实现 → 覆盖多个调度周期 → 归档 runbook → 删除 |
| **数据库字段** | 停止新写入 → 兼容读或双读验证 → 等待数据和回滚保留期 → 删除读取方 → 删除 schema；绝不能反向操作 |
| **消息字段或事件** | 停止生产 → 等待队列和重放保留期 → 验证所有消费者 → 做 schema breaking check → 删除消费者兼容逻辑 → 最后删除 schema |

GitLab 的 Feature Flag 清理文档明确建议，涉及数据写入或状态转换的 Flag 应跨多个 milestone 清理，并在代码引用、测试和 YAML 定义均删除、且版本部署到所有环境后，再删除 Flag 记录。 [^11]

对于 HTTP API，RFC 9745 将 `Deprecation` 定义为生命周期提示，并明确说明标记废弃本身不改变资源行为；需要表示停止服务日期时，可结合 RFC 8594 的 `Sunset` 。 [^12]

## 5.4 观察窗口如何确定

不存在适用于所有系统的固定“7 天”或“30 天”。

**\[综合建议\]**

例如：

- 每日任务：至少观察两个完整执行周期；
- 月结逻辑：至少跨越实际月结；
- 移动端接口：应覆盖最低支持版本退出周期；
- 灾备路径：不能依赖被动等待，应通过演练验证；
- 外部 API：观察窗口不能替代明确的废弃政策和客户迁移。

## 6\. 删除证据分级与决策矩阵

## 6.1 四类独立证据

多个工具只有在使用不同信息来源时才算独立证据。

| 证据族 | 例子 |
| --- | --- |
| **A. 静态与构建证据** | 编译器、调用图、数据流、Bazel cquery、包依赖图 |
| **B. 运行时证据** | 覆盖率、入口计数、Trace、Flag 评估、任务执行记录 |
| **C. 契约与组织证据** | API/schema、消费者契约、服务目录、跨仓搜索、owner 确认、Git 历史 |
| **D. 反事实与恢复证据** | 禁用入口、隔离运行、灰度、对照指标、回滚演练 |

`tsc` 和 ESLint 都发现某变量未用，通常仍主要属于同一静态证据族；而“静态不可达 + 生产入口计数为零 + owner/消费者确认 + 禁用入口后灰度正常”才是证据真正收敛。

## 6.2 建议评分模型

总分满分 100，再减去业务关键性惩罚：

| 维度 | 分值 | 建议评分 |
| --- | --- | --- |
| **静态可达性** | 0–15 | 0：未知；5：单工具；10：多分析与全部配置一致；15：编译器或完整 closed-world 图可证明 |
| **动态调用与覆盖** | 0–15 | 0：无数据；5：测试未命中；10：生产入口无命中；15：入口禁用后系统仍正常 |
| **观测窗口代表性** | 0–10 | 是否覆盖定时周期、峰值、地域、租户、权限、版本和故障场景 |
| **搜索与 Git 历史** | 0–10 | 全仓/跨仓/配置搜索、迁移 issue、最后修改原因；单纯“代码很老”最多只应贡献少量分数 |
| **所有权确认** | 0–10 | 无 owner 为 0；代码 owner 确认为中等；业务 owner 和已知消费者共同确认为高 |
| **外部接口与跨仓依赖** | 0–15 | 公开性未知为 0；服务目录部分登记为中；内部私有或所有消费者完成迁移为高 |
| **构建、测试与契约** | 0–15 | 从局部编译到全目标、集成、契约、升级、灰度逐步加分 |
| **可恢复性** | 0–10 | 不可逆数据变化为 0；普通 Git revert 为中；已演练的一键回滚且无数据损失为高 |
| **业务关键性惩罚** | 0 至 −15 | 一般内部工具 0；客户关键 −5；计费、数据、安全、权限、控制面、灾备 −10 至 −15 |

### 评分的特殊处理

- 检测到 **近期可信生产调用** ：不是扣几分，而是立即把候选状态改为“仍在使用”。
- 发现未知外部消费者：停止评分，进入消费者发现或废弃流程。
- 只有测试调用：不能直接称为生产 dead code，应先判断该测试是否验证仍支持的行为。
- Owner 表示下一版本或事故恢复仍需要：它不属于 dead code，而属于保留或路线图决策。

## 6.3 决策矩阵

| 类别 | 建议门槛 | 适用对象 | 必要动作 |
| --- | --- | --- | --- |
| **可自动删除** | 分数通常 ≥90；仅限低风险；无 veto；边界封闭 | 未使用局部变量、无副作用局部表达式、明确不可达分支、私有且编译器可证明的声明 | 自动生成小 PR；完整编译和相关测试；不得自动合并高影响变更 |
| **低风险人工确认后删除** | 通常 ≥75；风险为局部或模块内部；owner 确认 | 私有 helper、内部 package、无消费者的模块内依赖 | 代码审查、全目标构建、灰度和短期观察 |
| **需要迁移或废弃周期** | 即使高分，只要涉及公开、跨仓、动态、数据或多版本兼容 | 公共 API、SDK、CLI、事件、数据库字段、Feature Flag、移动端接口 | 阻止新增消费者、迁移、Deprecated/Sunset、观察、再删除 |
| **证据不足，暂不删除** | 分数不足；owner 未知；遥测或构建矩阵有空洞 | 反射、插件、运维脚本、灾备、地域分支、遗留系统 | 补建观测和测试；设置复查日期；不得无限期无说明 suppress |

## 6.4 直接阻止自动删除的条件

出现以下任一项，应绕过评分结果：

1. 公开 API、SDK、CLI、消息或数据库契约。
2. 未建模的反射、动态 import、依赖注入、插件或生成代码。
3. 数据写入、状态转换、迁移、回放或不可逆 schema 变化。
4. 计费、权限、安全、合规、控制面或故障恢复代码。
5. 外部消费者、跨仓消费者或移动端旧版本不明确。
6. 构建 target、平台、feature、region 或 tenant 矩阵不完整。
7. 只有低覆盖率、零 grep、代码年久或 IDE 提示等单一证据。
8. 没有明确 owner。
9. 没有代表性生产观测或观测存在已知盲区。
10. 没有可执行回滚方案。
11. 删除会同时改变行为和数据。
12. 候选代码具有加载、注册或初始化副作用。

## 7\. 各语言及构建生态的工具建议

## 7.1 语言生态

| 生态 | 推荐工具组合与维护状态 | 适用范围 | 主要限制 | 推荐接入方式 |
| --- | --- | --- | --- | --- |
| **Java / Kotlin** | IntelliJ/Qodana Unused Declaration；Error Prone；SpotBugs；detekt；JDK `jdeps` / `jdeprscan` ；JaCoCo；OpenRewrite。JaCoCo 最新正式版 0.8.15 发布于 2026-06-04，并支持 Java 26。 [^13] | 私有成员、依赖、字节码关系、deprecated JDK API、覆盖率、机械重写 | Spring/Jakarta/DI、序列化、反射、JNI、注解处理器； `jdeps` 是类或包依赖，不是源码级 dead-code 证明 | IDE/静态扫描先 report-only；配置框架入口注解；JaCoCo 合并单元和集成数据；最后才用 OpenRewrite 生成删除 PR |

| **Python** | Ruff F401/F841；Vulture；deptry；coverage.py。Vulture 2.16 发布于 2026-03-25；coverage.py 7.15.4 发布于 2026-08-06。 [^15] | 未使用 import、变量、函数、类、属性、依赖和运行覆盖 | decorators、Flask/Django 路由、entry points、 `importlib` 、monkey patch、 `__init__.py` re-export、editable install | Ruff 作为基础 CI；Vulture 按 confidence 分级并维护明确 whitelist；deptry 与脚本/配置搜索结合；coverage 合并 subprocess 和 integration 数据 |

| **C# /.NET** | Roslyn IDE0051、CA1812；trim analyzer/ILLink； `dotnet-coverage` | 未用 private 成员、部分 internal class、裁剪不安全路径、覆盖率 | 反射、序列化、DI、测试发现、XAML、source generator；CA1812 可能无法识别 NUnit 测试类 [^17] | IDE diagnostics 与 trim warnings 分开治理；不要仅 suppress trim warning；用正确反射标注或 source generation；执行 publish/trimming smoke test |
| **Rust** | rustc `dead_code` / `unreachable_code` ；cargo-udeps；cargo-machete；cargo-llvm-cov | 未用未导出项、Cargo 依赖、源码覆盖 | `pub` API、proc macro、 `build.rs` 、生成代码、feature、target、FFI；cargo-udeps 运行仍要求 nightly；cargo-machete 明确定位为快速但不精确 [^18] | 全 feature/target matrix；machete 用于快速候选；udeps 复核；为生成代码依赖维护带原因的 ignore；llvm-cov 合并 test/run 数据 |

### 特别限制说明

- Ruff 官方文档明确提示， `__init__.py` 中看似未使用的 import 可能是公开 re-export，自动修复可能不安全。 [^19]
- Vulture 的最高 confidence 也只保证“在被分析文件之内”未用；它提供 whitelist 和 decorator 忽略机制，说明框架入口仍需人为建模。 [^20]
- clang-tidy 的 `misc-unused-parameters` 只有在调用方位于同一 translation unit 时才能安全移除参数；include-cleaner 也主要处理当前主 translation unit。 [^21]
- Rust 的 cargo-machete 官方示例明确展示， `build.rs` 生成代码使用的依赖可能被误报。 [^22]

## 7.2 Monorepo、构建图和跨系统工具

| 工具或能力 | 适用范围 | 关键限制与正确定位 |
| --- | --- | --- |
| **Bazel query / cquery / aquery** | target 依赖、反向依赖、配置化 target、动作和生成 artifact | `query` 不理解具体配置； `cquery` 面向配置图； `aquery` 面向执行动作。它们解决 target 级闭包，不替代符号级调用图。 [^23] |

| **CodeQL 自定义查询** | 跨语言调用图、数据流和组织特定框架建模 | 不是开箱即用 dead-code 删除器；应把入口、隐式调用和公开 API 作为组织模型维护。 [^5] |

| **Buf breaking** | Protobuf schema 与历史版本的兼容差异 | 能检测会破坏客户端、服务器、生成代码或序列化数据的变化；不能证明某字段没有外部消费者。 [^27] |
| **PolyglotPiranha** | Feature Flag 输掉分支和相关代码的规则化清理 | Uber 主要用于 stale flag 清理，但官方仓库明确只优先支持 Uber 使用的语言；需针对组织 Flag API 编写规则。最新 0.4.8 发布于 2026-04-02。 [^28] |
| **OpenRewrite** | Java 等生态的 AST/CST 批量重构与清理 | 有未使用私有方法、字段和局部变量等 recipe；它只负责变换，不负责证明删除安全。部分 recipe 许可条件不同，应在企业接入前核对。 [^29] |

## 8\. 不同仓库形态的实施策略

| 场景 | 首选切入点 | 主要证据 | 风险重点 | 推荐推进方式 |
| --- | --- | --- | --- | --- |
| **单个模块试点** | owner 明确、测试较好、没有公开 API 和动态框架的内部模块 | 编译器、模块调用图、全模块测试、短期运行计数 | 模块边界是否真的封闭 | 先处理局部和私有声明；建立候选模板、评分和小 PR 习惯 |
| **大型单体仓库** | 按业务域、package 或部署单元划分 | 项目级入口、启动注册表、模块依赖、集成测试和生产 Handler 指标 | 隐式跨模块调用、共享全局状态、多个启动模式 | 一次只治理一个域；全量启动 profile 和回归套件；避免全仓一次性删除 |
| **Monorepo** | 先统一 target 和 owner 图 | Bazel/Buck/Nx 图、包发布信息、生成动作、全配置构建 | `select` 、feature、生成代码、共享 package、工具脚本 | 建立 target→owner→runtime service 映射；自动删除仅限 closed target 内的私有符号 |
| **多仓库微服务系统** | 服务目录、API gateway、schema 和 consumer catalog | 分布式 Trace、API 日志、Pact、Buf、跨仓搜索、包注册表 | 未登记消费者、第三方、异步消息、滚动版本兼容 | 优先治理 API/事件生命周期；很少对公开接口自动删除；迁移和废弃是主流程 |
| **缺少测试或可观测性的遗留系统** | 首先建立入口清单和 characterization tests | 启动 smoke、关键业务录制回放、入口计数、运维调查 | 所有“无调用”证据都可能是监控盲区 | 初期只删编译器能证明的局部无效代码；其他候选先隔离、埋点和归档，不做大批量删除 |

### 遗留系统的特殊原则

在缺少测试和可观测性的系统中，治理顺序必须调整为：

1. 资产盘点；
2. 关键行为 characterization test；
3. 稳定入口埋点；
4. 构建可重复化；
5. 可回滚发布；
6. 最后才扩大 dead-code 删除范围。

否则，清理项目只是把未知风险从代码库转移到生产环境。

## 9\. 30/60/90 天落地计划

## 0–30 天：建立边界、基线和可信试点

| 项目 | 建议 |
| --- | --- |
| **试点范围** | 选择 1 个 owner 清晰、无外部 API、测试和构建稳定的内部模块；排除计费、安全、权限、数据库、插件和灾备 |
| **工具接入** | 编译器/linter、一个项目级静态工具、构建图、代码搜索；全部使用 report-only |
| **基线** | 构建时间、CI 时间、依赖数、包体积、测试时长、候选数量、现有告警和 SLO |
| **治理定义** | 发布候选记录模板、风险分类、veto 条件、证据评分、PR 和回滚规范 |
| **团队协作** | 指定治理负责人、模块 owner、平台工程师、QA 和 SRE；确定候选确认 SLA |
| **实际清理** | 仅处理局部变量、明确不可达分支和无副作用私有声明；每个 PR 单一主题 |
| **衡量指标** | 候选精确率、误报原因分布、平均确认时间、PR 回滚率、构建和测试变化 |
| **30 天门槛** | 工具结果可重复；大部分候选能定位 owner；无清理导致的严重事故；团队能执行完整回滚流程 |

## 31–60 天：引入运行证据和反事实验证

| 项目 | 建议 |
| --- | --- |
| **扩展范围** | 增加一个含 Feature Flag 或内部 API 的模块，但仍避免公开客户接口 |
| **运行时证据** | 对 Handler、旧分支、job 和配置 key 增加低基数调用计数；明确采样率和缺失范围 |
| **消费者治理** | 建立跨仓搜索、服务目录、包和 API consumer 记录；CODEOWNERS 只作为责任线索 |
| **反事实实验** | 固定旧 Flag、暂停 job、从默认注册移除候选入口；保留一键恢复 |
| **验证能力** | 增加 integration、启动 smoke、Pact/Buf 或其他契约门禁 |
| **CI 策略** | 为存量结果建立 baseline；仅对净新增 dead-code warning 或无期限 suppression 失败 |
| **团队协作** | 建立每周候选 triage；SRE 审查观察窗和 stop condition；业务 owner 审批高风险项 |
| **60 天门槛** | 低风险候选能够从生成到删除形成闭环；运行时无调用数据可解释；至少完成一次回滚演练 |

## 61–90 天：扩大治理并有限自动化

| 项目 | 建议 |
| --- | --- |
| **扩大范围** | 覆盖更多模块或少量服务，但按风险和 owner 分批；不要直接全仓开启 fail-on-warning |
| **自动化** | 对满足 R0/高分条件的局部和私有候选自动创建 PR；仍要求 CI 和代码审查 |
| **Feature Flag** | 强制 owner、创建日期、类型、预期寿命和过期日期；对 stale 状态自动建单 |
| **公开接口** | 建立统一 Deprecation、替代项、消费者通知、Sunset 和 tombstone 规范 |
| **平台化** | 汇总静态、运行时、owner、契约和发布证据到一个 candidate dashboard |
| **持续治理** | suppression 必须有原因、owner 和 expiry；工具升级时重新评估 baseline 差异 |
| **效果评估** | 同时衡量工程收益和生产安全，而非单看删除代码行数 |
| **90 天扩大准入条件** | 候选精确率达到团队目标；关键环境和构建矩阵覆盖；无系统性误报；owner 响应机制有效；灰度与回滚成熟；清理导致的变更失败率可接受 |

### 推荐的扩大原则

治理范围扩大应基于：

- 候选精确率；
- owner 覆盖率；
- 运行时入口覆盖率；
- 构建矩阵覆盖率；
- 清理变更失败率；
- 回滚能力；
- 观察窗完成率；

而不是基于已经删除了多少行代码。

## 10\. 指标、反模式与停止条件

## 10.1 衡量指标

### 候选质量

还应记录：

- 按工具、语言和候选类型划分的误报率；
- 候选从发现到决定的 P50/P90 时间；
- 未找到 owner 的候选比例；
- 因动态调用、外部消费者或构建变体而暂缓的比例；
- suppression 超期率。

### 工程收益

- 全量与增量构建时间；
- CI 关键路径时间；
- 直接和传递依赖数量；
- 二进制、容器镜像、发布包和移动端包体积；
- 启动时间与内存；
- 测试数量、测试时长和 flaky rate；
- 构建 target、配置项、Flag 和运维资产数量；
- 依赖漏洞和许可证审查面是否缩小。

### 安全结果

- 清理变更失败率；
- 灰度停止率；
- 回滚率及回滚原因；
- 与清理相关的生产事故、告警、缺陷和客户工单；
- 错误率、延迟、可用性和业务指标相对 control 的差异；
- 未知消费者命中次数；
- 数据不一致、消息积压和重放失败；
- 发布后观察窗口完成率。

### 治理成熟度

- 有 owner 的模块、API、Flag、job 和 topic 比例；
- 有到期日的 Feature Flag 比例；
- 已废弃 API 中完成消费者迁移的比例；
- 新增 dead-code 候选趋势；
- 删除时是否同步清理依赖、配置、测试、文档和监控；
- 候选证据包完整率。

## 10.2 常见反模式

| 反模式 | 风险 | 替代做法 |
| --- | --- | --- |
| **仅凭 IDE 提示直接删除** | IDE 不知道外部消费者、反射和运行配置 | 将提示纳入候选；核对入口、消费者和构建矩阵 |
| **把低覆盖率等同于无用代码** | 覆盖不足可能正是测试缺陷 | 把低覆盖率当作“需要补观测或测试”的信号 |
| **只运行一个默认构建** | 漏掉平台、feature、region 和发布 target | 建立受支持配置矩阵并自动执行 |
| **一次提交删除大量不相关代码** | 难以审查、定位和回滚 | 按逻辑主题、小批次提交 |
| **删除实现但遗留配置和依赖** | 形成悬空资产、漏洞面和认知负担 | 使用完整性 checklist 清理代码、配置、测试、文档、监控 |
| **用自动 fix 代替决策** | codemod 只知道模式，不知道业务契约 | 自动工具仅生成 PR，删除许可来自证据模型 |
| **没有观察窗口** | 低频调用在上线后很久才出现 | 依据业务周期确定观察期 |
| **没有回滚机制** | 删除错误后只能紧急补丁 | 保留旧 artifact、Flag 或可执行 revert |
| **忽略外部消费者** | 破坏第三方、旧客户端或跨仓服务 | 服务目录、访问日志、契约和废弃周期 |
| **把 Git 年龄当删除依据** | 稳定而关键的代码通常很久不修改 | 查变更原因、调用和业务职责；年龄仅作为弱信号 |
| **为 LOC 指标而清理** | 鼓励删除测试、兼容和可读代码 | 关注复杂度、构建、依赖、事故和维护成本 |
| **永久 suppression** | 分析盲区不断累积 | suppression 必须附 owner、理由和过期日 |
| **删除新旧实现时同时做业务重构** | 无法区分故障来自删除还是新逻辑 | 迁移、固定流量、删除、优化分阶段完成 |

## 10.3 必须停止发布或立即回滚的条件

出现以下任一项应停止扩大灰度：

- 被停用入口出现任何无法解释的真实调用；
- 出现未知 consumer ID、旧客户端版本或第三方调用；
- 契约、schema、升级或滚动部署测试失败；
- canary 相对 control 的错误率、延迟或业务指标越过预设阈值；
- 数据对账、消息积压或状态转换出现差异；
- 特定地域、租户、权限或平台异常；
- SLO 消耗或告警显著增加；
- 发现观测缺失、采样配置错误或埋点未部署；
- 回滚资产不可用；
- 模块、业务、数据、安全或 SRE owner 提出未解决异议。

阈值必须在发布前设定，而不能在指标恶化后临时解释。

## 11\. 可直接复用的清理检查清单

## 11.1 候选和边界

- 已说明候选是代码、依赖、配置、API、Flag、job、topic 还是 schema。
- 已列出仓库、模块、服务和部署范围。
- 已列出所有入口：HTTP、RPC、CLI、消息、任务、脚本、插件、测试和生成器。
- 已列出平台、架构、profile、feature、region、tenant、权限和版本矩阵。
- 已确认它不是生成产物，或已经检查生成源。
- 已检查 import、初始化、注册和其他副作用。
- 已标记业务关键性和数据影响。
- 已明确代码 owner 和业务 owner。

## 11.2 静态和消费者验证

- 至少一种静态工具可重复报告该候选。
- 对非局部候选，已有第二种不同原理的验证。
- 已搜索符号、字符串、路由、topic、配置 key、类名和文件名。
- 已搜索当前仓库、相关仓库、IaC、CI、脚本和文档。
- 已检查 Git 历史、迁移 PR、issue 和原始设计目的。
- 已检查 CODEOWNERS、服务目录、API/包注册表。
- 已识别所有已知消费者并取得确认。
- 已核对公开 API、SDK、CLI、消息和 schema 兼容要求。
- 已检查移动端和其他长期存活客户端。
- 不存在仍未解决的动态调用或插件路径。

GitHub 的 CODEOWNERS 可以要求特定 owner 审批 PR，代码搜索可以跨仓定位符号； `git log -L` 和 `git blame` 可用于追踪函数或代码行历史。但这些工具只能帮助发现责任和上下文，不能单独证明无人使用。 [^30]

## 11.3 运行时和废弃过程

- 已明确运行时数据采集范围、采样率和盲区。
- 已按地域、租户、权限、版本和环境分桶检查。
- 观察窗口覆盖最慢业务周期。
- 定时和低频路径已实际执行或演练。
- 对旧入口增加了可定位消费者的命中告警。
- 已阻止新增调用方或新依赖。
- Feature Flag 已在所有环境固定到最终状态。
- API 已提供 Deprecated 标识、替代项和迁移说明。
- 外部接口已完成必要的 Sunset 和通知窗口。
- 已执行停入口、暂停任务或移除注册的反事实验证。

Unleash 将 Flag 区分为 active、potentially stale 和 stale，并通过客户端评估指标记录启用和禁用次数；这些能力适合用于生成和验证候选，但 stale 状态本身仍不是删除许可。 [^31]

## 11.4 删除变更

- 迁移、禁用和实际删除没有混在同一个不可审查 PR 中。
- PR 只覆盖一个逻辑主题。
- 没有混入无关格式化、依赖升级或重构。
- 已删除所有调用入口和注册项。
- 已检查参数、接口、构造函数和序列化格式变化。
- 已检查加载或初始化副作用。
- 机器生成的 diff 已人工检查。
- PR 描述包含证据链接、风险分级和回滚步骤。
- 代码 owner、业务 owner 及必要的 SRE/数据/安全负责人已审批。
- 删除前版本或 artifact 仍可获取。

## 11.5 构建和验证

- 全部受支持 target、profile 和平台构建通过。
- 单元、集成、端到端和启动 smoke test 通过。
- 测试发现列表未意外减少。
- API 和消费者契约测试通过。
- Protobuf、消息或其他 schema breaking check 通过。
- n/n−1 滚动部署或升级兼容测试通过。
- 发布包、容器、CLI、插件和示例构建通过。
- 数据对账和消息积压正常。
- 没有无说明的测试 skip 或分析 suppression。
- 回滚流程已经验证。

## 11.6 发布与收尾

- 已定义 canary 范围和 control。
- 已预先定义错误、延迟、业务、数据和资源 guardrail。
- 已定义停止条件和决策人。
- 旧入口命中告警已经部署。
- 回滚镜像、配置、Flag 或 commit 已准备好。
- 完整观察窗口已结束。
- 未出现未知消费者、生产回归或相关工单。
- 已同步删除依赖、配置、Flag、测试、文档和监控。
- 已更新服务目录、架构图和 runbook。
- 已归档证据包和最终决策。
- CI 已配置为防止相同类型的 dead code 再次进入。
- suppression 或保留项已有 owner 和下次复查日期。

## 最终结论

**可以删除** ，必须同时满足：

- 分析边界足够封闭；
- 没有可信正向调用；
- 静态、运行时、消费者和契约证据相互独立且一致；
- 高风险动态机制已经建模；
- 必要迁移、废弃和观察窗口已经完成；
- 删除前的禁用或隔离实验成功；
- 全目标构建、测试、契约和升级验证通过；
- 生产可以灰度、监控和快速回滚。

**不能删除** ，只要存在：

- 未知消费者；
- 未解决的动态入口；
- 不完整的配置或构建矩阵；
- 未覆盖的低频、地域、权限、旧版本、灾备或数据路径；
- 公开接口尚在支持期；
- 唯一证据只是 IDE、grep、低覆盖率或 Git 年龄；
- 删除不可逆或无法可靠回滚。

**删除后证明系统安全** ，不是声称获得永久、绝对的数学证明，而是在明确的系统边界、支持版本和观察期限内，用：

1. 删除前反事实禁用；
2. 确定性构建与测试；
3. 消费者和 schema 契约；
4. 灰度对照；
5. 生产 SLO、业务与数据指标；
6. 未知调用告警；
7. 完整观察周期；
8. 可执行回滚；

建立一条可审计、可复现、可回退的工程证据链。
